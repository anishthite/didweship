API contract

Lookup (cached in JSON; re-run only on handle change)

GET /2/users/by/username/{handle}
Authorization: Bearer $X_BEARER_TOKEN          // app-only
→ { "data": { "id": "...", "username": "..." } }   // $0.010/user

Timeline (paginated)

GET /2/users/{id}/tweets
  ?max_results=100
  &tweet.fields=created_at
  &exclude=retweets,replies       // originals only (D-002)
  &since_id={last_tweet_id}       // mode A: steady state (D-001)
  &start_time={YYYY-MM-DD}T00:00:00Z  // mode B: one-time migration/backfill window
  &pagination_token={meta.next_token}
→ { "data": [{ "id", "created_at" }], "meta": { "next_token"?, "newest_id" } }

3200-most-recent ceiling per user; meta.newest_id from page 1 is the next since_id. 402 = out of credits (non-retryable, loud error).

Algorithm

  1. Load roster from users.json; per slug, load existing data.
  2. Resolve user_id (cached; else lookup).
  3. Mode pick: last_tweet_id present → since_id; else start_time = max(days) − 2d (or BACKFILL_SINCE on empty days[]).
  4. Fetch pages; bucket each created_at via Intl.DateTimeFormat("en-CA", {timeZone: NERV_TZ}) (matches streak.ts dateKey()).
  5. Merge: since_id mode → additive (count += fresh); start_time mode → replace dates ≥ since, never touch older.
  6. Store last_tweet_id = meta.newest_id (only on fully-completed fetch with posts seen).
  7. Refuse commit if merged days[] shrinks; atomic write via tmp+rename; per-user failure isolation (all-fail → exit 1).

Decisions

IDChoice · Rationale
D-001since_id incremental for steady state over repeating the 2-day start_time overlap. Per-post billing re-bills overlap re-reads; since_id bills each post once.
D-002exclude=retweets,replies — "shipped" = original posts only. User decision; changes semantics vs socialdata from: search (which counted RTs).
D-003Hourly cron (7 * * * *). User decision; billing is per-post so quiet hours cost ~$0; rate limit (~5 req/15min/app) fits 2 users trivially.
D-004Keep commit-back-to-git flow unchanged. Render path stays bundled-JSON; zero app changes; Vercel rebuild per data commit as before.
D-005No re-backfill at migration. Existing socialdata-built days kept; one start_time overlap fetch bootstraps last_tweet_id per user. Saves ~$30+ of pointless re-reads.
D-006No date-window sharding in the rewrite. Timeline paginates via next_token; backfill is a one-time-per-user path, sequential is fine.
D-007Drop LATEST_ONLY env mode. since_id subsumes it at equal-or-lower cost.

Tradeoffs

IDPicked over Rejected · Reason
T-001Official X API (~$1–3/mo) over socialdata.tools (~$0.03/mo). Real-time freshness + no third-party cache lag/quota-trimming; user picked quality over cost explicitly.
T-002Additive merge (since_id mode) over replace-window. API only returns strictly-new posts there; deleted posts keep their count — accepted noise for a binary ship signal.
T-003Clean swap over keeping a socialdata fallback flag. Git history is the rollback; a second live code path is dead weight.
T-004api.x.com over api.twitter.com. Same service; canonical host.

Assumptions

  • A-001 · Pay-per-use bills per post returned; empty since_id results ≈ $0. If there's a per-request floor: hourly cadence cost rises (~$3.50/mo at $0.005/call flat) — still trivial.
  • A-002 · User timeline rate limit at the user's tier ≥ 48 req/day. Docs say ~5 req/15min/app on low tiers → 480/day, 10× headroom.
  • A-003 · Existing socialdata day-counts are historically accurate enough to keep. If wrong: clear a slug's days[] + last_tweet_id to trigger a paid re-backfill (~$15/user worst case at 3200-post ceiling).

Reversibility

R-001 · medium. Until X_BEARER_TOKEN is set in Actions secrets, the workflow exits 2 at the refresh step — no commit, old data persists, no corruption. Full revert: git checkout 5bac392 -- scripts/refresh-x-days.ts .github/workflows/refresh-x-days.yml + keep SOCIALDATA_API_KEY secret. The last_tweet_id JSON field is ignored by the old script (loose parse), so the data file is compatible both directions.
